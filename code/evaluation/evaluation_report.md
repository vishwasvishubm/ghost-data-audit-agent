# Evaluation Report: Ghost Data Still Exists

## What is evaluated, and how

The agent's output for each request is a deletion status plus an ordered `steps_json`. It is
evaluated at three levels:

1. **End to end against gold.** The 32 public samples are predicted and compared with
   `dataset/sample_output.csv` (`code/evaluation/main.py`):
   - *case-level status accuracy*: `deletion_status` matches;
   - *step precision/recall/F1*: steps matched as `(phase, system_id, resource_id, operation, state, evidence_id)` multisets;
   - *field accuracy*: per-field agreement of position-aligned steps;
   - *sequence accuracy*: the whole `steps_json` array is identical, order included (the strictest measure).
2. **Custom cases** (`code/evaluation/custom_cases.py`): variants of real requests, each changing one
   thing on purpose, with the expected outcome written down from reasoning before running.
3. **Component checks**, so a failure can be located: evidence parsers vs every evidence citation in
   the gold samples, screenshot transcription vs a hand reading of the images, the intent classifier
   vs hand labels of every distinct request text, and identity/link recall on gold resources. The
   submitted `output.csv` (518 rows, no gold) is checked against the output contract and for any
   citation of evidence captured after a case's `audit_at`.
4. **Regression and adversarial suite** (`code/evaluation/regression_tests.py`): 20 tests covering 15
   required scenarios, from historical identifiers to malformed and contradictory evidence. Expectations
   are written into each test before it runs; the 3 tests with fabricated inputs are labeled synthetic.

Everything is reproduced by one command, which regenerates the results section below:

```bash
python code/evaluation/run_all.py
```

Failures found along the way, and their fixes:

- **Citing evidence from the future.** A bundle exported 09-17 contains sub-snapshots dated 09-15;
  using them for a 09-15 audit produced citations the gold never makes. Fix: evidence is available at
  `max(record time, file capture time)`.
- **Replica drift hidden by later listings.** A failover replica still held `account_005` after the
  primary dropped it; a later empty primary inventory had overwritten that. Fix: each copy (service,
  read/regional/reporting/failover replica) keeps its own state and the record exists if any copy does.
  A bug that collapsed all replicas into "primary" was found and fixed in the same step.
- **Filtered listings mistaken for full ones.** A bundle's security-event listing only contains two
  subjects' events, which made every other retained audit record look deleted. Fix: omission can only
  prove a deletion, never that a retained record disappeared, and a direct read outranks a listing.
- **Identifier-free records.** Deleted accounts and anonymized analytics profiles carry no identifier,
  so evidence alone linked 83/111 gold resources. Analysis of the activity stream showed the deletion
  worker acts 45-75 minutes before each case's `reported_at`, and the primary-profile delete's result
  always matches the case's reported status (SUCCESS/PARTIAL/FAILED for COMPLETE/PARTIALLY_COMPLETE/NOT_STARTED).
  Attribution by window + status + evidence ownership + batch elimination raised link recall to 96/111.
- **Wrong document mapping.** The customer-statement PDF was first mapped to `export_1260` by its
  order number; the data catalog maps its statement number to `export_1842`. Fix: catalog aliases
  resolve all business names shown in documents and screenshots.
- **Intent edge case.** "The privacy page still says my request failed... tell me whether the account
  ... has been removed" was classified as an access request (397/398 texts). The prompt now states that
  follow-ups on a deletion request are deletion; 398/398.
- **Cost and latency.** Default thinking made one screenshot take 232 s and 2,427 output tokens; low
  thinking gave the same transcription with 523 output tokens.
- **Operational.** The Gemini free tier allows 20 requests per model per day. Calls are now cached,
  batched (100 texts per intent call), fail fast on daily quotas and back off on per-minute limits.
- **Elimination missed forced assignments (case_18).** Two other cases in the batch both had exactly
  the candidates {`account_5193`, `account_5823`}, so between them they must use both, which leaves
  `account_5521` to case_18. The old elimination only removed a resource when one other case claimed it
  alone, and only looked at cases reported within 80 minutes. Fix: attribution is a maximum bipartite
  matching (subjects to candidate resources) over the whole connected group of cases sharing
  candidates; a subject gets a resource only if every maximum matching gives it that resource.
  Regression test: `batch_resolved_by_matching`; symmetric ties stay untouched (`ambiguous_batch_not_guessed`).
  Effect on the full dataset: 18 of 518 rows gained verification steps (16 deleted accounts, 2
  anonymized analytics records); no status changed and no step was removed.
- **Retention periods were not enforced.** Rules 12 and 13 keep security logs only within their
  retention period and legal-hold records only while the hold is active, but every such record was
  retained. Fix: a lapsed retention date turns RETAIN into DELETE. No record in the public data has
  lapsed by its audit, so outputs are unchanged; the synthetic test `retention_period_expiry` covers it.
- **One corrupt file could stop every audit.** A parser exception aborted the whole run. Fix: each file
  is parsed in isolation; failures are reported and skipped (synthetic test `malformed_evidence`).

## Remaining failures and limitations

All remaining sample differences are **missing verification steps**; no predicted step is wrong
(step precision 100%). They fall into two groups:

- **Workflow batch ties.** When several requests in one deletion batch share a reported status, and
  none of their deleted accounts or anonymized analytics records has an identifier anywhere in the
  evidence known at audit time, the records cannot be told apart. The agent reports these as ties and
  emits nothing for them rather than guess. Ties are symmetric: the tied subjects have identical
  candidate sets, so no assignment is better supported than another (e.g. case_28 and case_29 are both
  NOT_STARTED and share the same two FAILED account deletes). On the evaluation requests that authorize
  deletion, 110 have a tied primary account and 203 a tied anonymized-analytics candidate (many of the
  latter already have their analytics record from evidence). Relaxing the audit-time cutoff for
  ownership would resolve some ties (the 10-01 handover names the other owners in case_31's and
  case_32's batches) but would let evidence created after the audit change the answer, which the rules
  forbid, so it is not done.
- **Unreachable records.** `account_004` (case_04) and two security audit records (case_18, case_20)
  appear in no evidence file and no activity row available to participants.

Other limitations: the agent's rules were developed against 32 public samples, so behaviour on
unseen patterns is checked by the custom cases, the regression suite and the contract checks, not by
gold, and public-sample scores do not predict the hidden evaluation; screenshot reading relies on a
vision model (verified 32/32 resources and 52/52 fields against a hand reading); request texts and
screenshots are untrusted input to the models, and no defence beyond fixed schemas and deterministic
interpretation is implemented against instructions embedded in them; model prices in the usage
report come from third-party aggregators.
